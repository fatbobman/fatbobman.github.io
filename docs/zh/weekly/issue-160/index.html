快速消失的硬盘容量

我的 MacBook 上几乎只保存与开发有关的工具和数据，长期空闲容量至少保持在 500～600 GB，因此在相当长的一段时间里，我都认为内置的硬盘容量绰绰有余。但 Agent 改变了这种情况——上周，我接连遭遇了两次硬盘空间在短时间内被迅速耗尽的窘境。

第一次，是因为 Agent 在开发过程中不断产生大量数据，而相关目录仍被包含在 Time Machine 的备份范围内。随着文件持续创建、修改和删除，本地快照保留的数据块不断累积，最终占用了大量磁盘空间。直到我将这些目录加入备份排除列表，并清理掉已有的本地快照后，问题才得以解决。

第二次，则是 Agent 自己编写的测试脚本存在清理漏洞：调用 mkdtempSync 创建临时目录后，却没有对应的清理操作。每执行一次 QA 流程，就会完整解包一份 5.7 GB 的 Design 仓库。随着测试不断重复，硬盘里很快堆积起海量的垃圾数据。

有意思的是，两次问题最终都是在 Agent 的协助下解决的，但起因却也都是它。相较于人类开发者习惯的线性工作节奏，Agent 往往会以更加激进、并行化的方式推进开发。这使得除了 CPU 和 RAM，硬盘存储也开始成为这种全新工作流下不可忽视的瓶颈。而苹果「金子级」的存储定价又是出了名的昂贵。相信不少开发者在选购适合当下开发需求的新设备时，看到最终的配置单价格，都会忍不住倒吸一口凉气。

AI 的“繁荣”让内存与闪存的价格在短时间内大幅提升，而全新的开发方式又倒逼着开发者不断升级硬件，一切仿佛陷入了一种奇妙的“军备竞赛”。

不过，除了花钱购买更大的存储容量，我们或许更需要尽快适应这种工作范式的转变：为 Agent 划定更加清晰、严格的环境边界，建立可靠的资源管理与清理规范。否则，再大的硬盘容量，也经不起 Agent 毫无节制的暴力消耗。

近期推荐

Swift Optional 的进阶妙用 (Interesting ways of using Swift optionals)

Optional 是 Swift 中最基础、最常用，也最具特色的类型之一。围绕它，Swift 提供了丰富的 API 和语法糖。但除了 if let、guard let 和可选链之外，Optional 还有不少值得挖掘的能力。⁠John Sundell 在本文中介绍了几种有趣且不太常见的用法：take() 将两个操作合二为一，在取出包装值的同时将变量重置为 nil；对 Optional Enum 进行 switch，将 nil 与各个枚举 case 放在一起处理；通过 map、flatMap 构建连续的数据转换链；以及利用泛型约束和 KeyPath 扩展 Optional，封装可复用的判断逻辑。

初学 Swift 时，我总会惊叹于 Optional 提供的各种小技巧。或许如今你已经不再经常亲手编写代码，但这些技巧依然能让你重温 Swift 语言本身的魅力。

用 Instruments 排查 SwiftUI 视图重绘 (SwiftUI Performance: Find Redraws in Xcode Instruments)

⁠Antoine van der Lee 以一个刻意制造性能问题的 SwiftUI 应用为例，展示了如何利用 Xcode Instruments 的 SwiftUI 模板定位性能瓶颈：通过 View Body Updates 的层级视图找出累计耗时较高的视图，借助更新明细表查看每次 body 执行的耗时及 Root Causes，再利用因果关系图追踪状态变化与视图更新之间的联系。

Antoine 提醒读者，分析 SwiftUI 性能时，不能只关注单次 body 执行的耗时，还需要结合更新频率与触发原因，才能更准确地判断问题所在。

认识 iOS 27 全新 Now Playing 框架 (iOS 27: Now Playing Framework)

长期以来，iOS 的媒体元数据、播放状态和远程控制能力分散在不同的 API 中。iOS 27 引入的 Now Playing 框架，将这些能力整合到统一的媒体会话模型中。⁠Anton Gubarenko 展示了如何通过 MediaSessionRepresentable 描述媒体内容、使用 MediaPlaybackSnapshot 提供播放状态快照，并通过 MediaCommand 声明系统可以执行的播放操作。

除了简化本地媒体播放的系统集成，新框架还支持远程媒体会话（Remote Media Session）。借助 App Extension 和推送通知，即使主应用没有运行，也能在锁屏和控制中心呈现外部扬声器、电视等设备的播放状态，并响应用户的控制操作。

适配 iPhone Duo：折叠屏上的 SwiftUI 布局探索 (Positioning SwiftUI views around the fold on iPhone Duo)

在适配 iPhone Duo 时，如何让视图在设备折叠与展开过程中保持自然、稳定的呈现，是开发者面临的新挑战。⁠Natalia Panferova 在本文中提出了一个重要思路：适配不只是避开硬件限制，还需要考虑设备形态变化时的视觉连续性。

Natalia 介绍了如何利用 GeometryProxy.reservedRegions(kind:options:) 的 .includeInactive 选项，提前获取尚未激活的折叠区域，为折叠状态做好布局准备。通过预先确定网格列数，并在折叠过程中动态调整列宽与间距，让内容始终分布在折痕两侧，避免因列数变化导致内容位置大幅移动。

不止于字符串：SwiftUI Text 插值技巧 (SwiftUI Text Interpolation Beyond Plain Strings)

尽管 Text("Hello, \(name)") 看起来与 String 的插值语法类似，但背后使用的实际上是 LocalizedStringKey 提供的一系列专用插值方法。它不仅能插入字符串，还能直接处理数字、日期、Text、Image 等类型，并根据不同地区的语言和格式习惯呈现内容。

⁠Stewart Lynch 介绍了 Text 插值的多种用法：通过 FormatStyle 格式化货币、百分比和日期；使用 style: 与 timerInterval: 实现自动更新的相对时间和倒计时；在同一句话中嵌入不同样式的 Text 或 SF Symbols；以及在需要根据运行时数据设置文本样式时使用 AttributedString。另外，相比直接拼接多个 Text，插值可以保留完整的本地化语句，让翻译人员根据语言习惯重新排列内容，而不受原始拼接顺序的限制。这也是 Text 的 + 拼接操作符从 iOS 26 开始被弃用的重要原因。

无感演进：框架 API 变更的设计艺术 (The Best API Change Is the One Nobody Notices)

为 Swift 框架增加新能力，如果涉及增加泛型参数、修改协议要求，往往会破坏兼容性，甚至要求现有用户迁移代码。⁠Michael Long 以依赖注入框架 Factory 新增 Scene 级自定义容器支持为例，展示了如何通过调整内部设计，在基本保持公开 API 不变的情况下完成扩展。为了避免修改现有属性包装器的泛型签名，他选择将不同容器类型的差异从类型系统转移到数据层，通过单一 Environment Key 和基于 ObjectIdentifier 的注册表管理多个容器实例，并在未找到对应 Scene 容器时回退到原有的共享实例。

文章还介绍了如何通过计算属性保留既有的 Environment API，以及利用 DynamicProperty.update() 让 @InjectedContainer 在 SwiftUI View 中读取 Scene 容器，同时维持普通类中的原有行为。

Michael 的实践展示了一个值得框架作者思考的问题：新能力不一定需要以破坏性 API 变更为代价，关键在于找到合适的内部抽象边界，并在类型安全、向后兼容、SwiftUI 环境机制和 API 简洁性之间做出权衡。

在同一 Xcode 项目中安全并行多个 Claude Code Agent (Run Multiple Claude Code Agents on the Same Xcode Project)

让多个 Agent 并行开发同一个 Xcode 项目正变得越来越普遍。但即使通过 Git Worktree 隔离了源代码，也不意味着构建与测试环境同样实现了隔离。例如，两个 Agent 都报告构建成功，但由于共享同一个 Simulator，后安装的应用覆盖了先前的版本。这意味着 Agent 可能在不知情的情况下，运行并验证了另一个 Agent 构建的应用，导致测试结果失去可信度。

⁠Amarildo Lucas 分析了这一问题的成因，并讨论了如何通过独立的 DerivedData、Simulator 和构建配置减少并行 Agent 之间的相互干扰。Amarildo 提醒开发者：多 Agent 协作需要隔离的不只是代码，还包括构建产物、运行环境与验证过程。

Apple 中国区 App Store ICP 备案例外申请

对于希望在中国大陆 App Store 上架应用的开发者来说，ICP 备案可能是一道不小的门槛，尤其是缺乏中国大陆服务器及相关备案条件的海外独立开发者。不过，对于主要在本地运行、不依赖自建服务器的 App，Apple 提供了一条例外申请途径。

⁠方君宇 分享了为自己申请 ICP 备案例外的完整经历。从通过 Apple Developer 联系页面提交申请，到准备包含开发者信息、App ID 和相关声明的信函，再到上传 PDF 材料并获得批准，整个流程耗时约 6 天。文章还提供了声明信函模板及各个环节的操作说明。当然，这项例外申请并非自动适用于所有离线 App，Apple 的批准也仅针对申请的特定 App，也不代表免除其他适用的法律法规要求。

工具

SwiftyDMG：原生 SwiftUI 的 DMG 镜像制作器

对于在 Mac App Store 之外分发应用的开发者，制作一个布局得体的 DMG，也是发布前值得打磨的一环。⁠Chocoford 开发的 SwiftyDMG 将这套工作流带入了原生 SwiftUI 界面：拖入 .app，便可在实时预览中调整应用图标与 Applications 文件夹快捷方式的位置，设置窗口尺寸、自定义背景和磁盘图标，再生成安装镜像。它还提供 Finder 右键服务和详细的构建日志，方便快速打包与排查问题。

PreviewMD：macOS 上的 Markdown 快速预览与阅读器

Markdown 已经成为开发者文档的主要格式之一，但遗憾的是，macOS 的 Quick Look 至今没有内置完整的 Markdown 渲染预览能力。⁠Adam Jesionkiewicz 开发的 PreviewMD 补上了这个缺口：在访达中选中文件、按下空格，就能预览排版后的标题、表格、任务列表、代码和本地图片。它还附带独立阅读应用，可以直接打开现有文件夹，浏览文档、渲染 Mermaid 图表、跳转 Obsidian 双向链接，并在预览、分栏和编辑模式之间切换。

szt：Swift 编写的超高速磁盘分析命令行工具

Tommi Urtti 开发的 szt（sizetree）是一款使用 Swift 开发的开源命令行工具，可以快速扫描指定目录，并以彩色树状结构展示磁盘空间的占用情况。它会优先展开占用较大的目录，将次要内容折叠起来，让开发者能够迅速定位空间消耗的主要来源。

szt 的另一个亮点是性能。它通过 macOS 的 getattrlistbulk 批量获取文件元数据，并利用多线程并行扫描。在作者的测试中，扫描包含 66.7 万个文件、总计 123 GB 的目录仅需 2.4 秒，而传统 du 命令需要约 17 秒。在上周我碰到的磁盘空间异常快速消耗的问题中，szt 帮我加快了排查过程。
